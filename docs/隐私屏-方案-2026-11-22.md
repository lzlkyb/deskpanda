# 隐私屏 · 方案稿(仅设计,未实现)

> 2026-11-22 · 竞品借鉴清单 ③(来源:RustDesk/CrossDesk 对照,🔴 AGPL/GPL
> 代码绝不抄,只借鉴思路)。本文回答「做一个真的隐私屏要付出什么」,
> 结论是**虚拟显示器驱动级专项**,不在常规迭代里排期。
> 状态:**待 owner 决策**(立项/搁置/放弃)。

## 0. 语义与需求

隐私屏 = **远程会话期间,被控端的物理屏幕不显示会话内容**(黑屏/锁死),
而发起端照常看到画面、操作键鼠。典型场景:用户在咖啡馆远程办公室电脑,
不想让旁边人看到办公室屏幕上的内容。

注意与现有机制的区别:DeskPanda 已有「暂停推送画面」(`rcVideoPauseSet`,
丙-③)——那是**发起端看不到**;隐私屏是**被控端旁边的人看不到**,
方向相反,不能互相替代。

## 1. 为什么廉价路线全部无效(实查结论)

| 路线 | 为什么不行 |
|---|---|
| 只关屏(`SC_MONITORPOWER`/显示器休眠) | **任何输入都会唤醒屏幕**——而远程注入的键鼠恰是输入,等于边控边亮,完全无效。这是 RustDesk 也绕不开的根问题 |
| 截屏后盖黑窗 | 键鼠焦点/Alt-Tab/Ctrl-Alt-Del 全部穿透;安全桌面(UAC)直接越权;给用户假安全感比没有更糟 |
| 换桌面(`SwitchDesktop`)/锁屏 | 会话采集面(DXGI 绑输入桌面)与登录态一起被切掉,画面即断;这正是原仓 S4/S6「锁屏可操作」专项要解的另一头 |
| macOS 任何用户态方案 | macOS 无用户态虚拟显示器机制;`CGDisplayCapture` 独占会破坏 ScreenCaptureKit 采集。**RustDesk 在 macOS 也不支持隐私屏**——不是它没做完,是平台无路径 |

## 2. 唯一可行路线:虚拟显示器(Windows)

RustDesk 的 Windows 实现即此:安装一个 **IddCx(Indirect Display Driver)**
虚拟显示器 → 会话期把桌面**切到虚拟显示器**(物理屏黑/移出桌面)→
采集虚拟显示器 → 结束时切回物理屏。远程键鼠注入作用在虚拟屏的桌面上,
物理屏没有内容可显示,也就不存在「唤醒泄密」。

### 阶段拆分(预估 3-5 周,驱动工程是主体)

| 阶段 | 内容 | 风险/量级 |
|---|---|---|
| D1 驱动工程 | IddCx 驱动(WDK):设备创建/移除/分辨率适配。可评估开源样例(IddSampleDriver,MIT)作起点,但**必须自建工程自持代码** | 1-2 周;需要 WDK 工具链与驱动测试 |
| D2 签名与安装 | 测试签名 vs 正式签名(EV 证书 + WHQL,年费级成本);安装器集成(NSIS/WiX)、卸载清理 | **成本大头**:正式签名走 WHQL 认证,周期与费用需 owner 拍板;不签名则用户要开测试模式,产品上不可接受 |
| D3 会话编排 | 切换物理↔虚拟屏(与 ② 分辨率调节的 `display_mode` 基建有协同:都是显示拓扑变更,DXGI/SCK 采集重建路径共享);崩溃还原兜底(复用 ② 的 pending-restore 思路) | 3-5 天 |
| D4 验收 | 双机 + 拔线/睡眠/UAC 弹窗/多屏组合;安全审计(物理屏在任何输入下都不漏画面) | 2-3 天 |

### 与现有代码的协同点

- 采集端对「显示拓扑瞬变」的熔断重建设计(`rc/dxgi.rs:311-360`)与 ② 分辨率
  调节的采集重开路径,正是 D3 需要的地基——② 先行可以把这段路趟熟。
- 会话期系统状态 RAII(`rc/keep_awake.rs` 的字段模式 + `end_session` 单一收口)
  直接复用为虚拟屏的还原保证。

## 3. 建议

1. **暂不立项**:成本集中在驱动签名(外部费用/周期),不在工程能力;
   在没有明确的企业/付费用户诉求前,性价比低于 backlog 其他项
   (Windows 服务级无人值守、TCP 隧道)。
2. **若立项**:优先级排在 iroh 1.5 升级(卡 relay 版本)与 P1-c 验收之后;
   D2 的签名方案(测试签名自用 vs WHQL 发布)是 owner 级决策,立项前先定。
3. **macOS 永久不做**:平台无路径,UI 上如实标注即可(参照 rcPlatform 的
   诚实降级口径),不承诺。
