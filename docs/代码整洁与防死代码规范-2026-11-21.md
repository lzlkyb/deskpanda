# 代码整洁与防死代码规范

> 2026-11-21 立档。回答一个问题：**以后怎么保证不积死代码、结构持续清晰。**
> 本文是 `docs/协作开发规范-2026-11-20.md` 的工程补充（那边管人与流程，这边管代码体质），
> 冲突时以本文的代码规则为准。
>
> 依据（2026-11-21 调研，文末附录有探针实录）：
> - [Knip 官方文档](https://knip.dev)——JS/TS 死代码检测的行业标准（月下载 86M、21k+ 项目在用；
>   前代工具 ts-prune / depcheck 均已归档并指向 Knip）
> - Ford / Parsons / Kua《Building Evolutionary Architectures》（2017）——架构适应度函数
> - [Theodo：ts-prune 死代码策略](https://www.theodo.com/en-fr/blog/seek-and-destroy-dead-code-for-good-a-strategy-using-ts-prune)——棘轮灭零法
> - [Rust Project Primer: Unused Dependencies](https://rustprojectprimer.com/checks/unused.html)——cargo-machete / cargo-udeps 分工
> - [cross-stack-standard ADR 0062](https://github.com/o6b7/cross-stack-standard/blob/main/docs/decisions/0062-frontend-layer-boundaries.md)——「一条规则一道闸」的分层执法
> - Uncle Bob《Clean Code》——童子军军规

## 0. 核心思想：死代码是「每一班岗」的事，不是「大扫除」的事

行业数据与教训一致：**大扫除式清理永远追不上腐烂速度**。本项目 2026-11-20~21 两轮清掉约 5900 行
死代码，全部是迁移（PastePanda→DeskPanda）与功能下线后的残留——如果每一班岗都守住，这些代码
根本不该有机会活到被清理那天。

所以规范围绕三道防线，全部**自动化、进门禁、不依赖自觉**：

```
第一道  进不来  门禁 fitness function（knip / machete / clippy）  新死代码提交不进来
第二道  躲不住  结构边界（分层 + 域隔离 + 导出最小化）             死代码没有容身之处
第三道  积不起  流程与文化（童子军军规 / 删除四查 / 债档）          存量只减不增
```

> **名词对齐**：Neal Ford 把「对架构特性的客观自动化评估」称为 *fitness function*（适应度函数）。
> 本仓库已有的 **组件体量门禁**（`scripts/check-component-size.mjs`，基线只降不升）和
> **对账测试**（`RcSettingsWiring.test.ts` 五环接线、`RcTargetDeviceMirror.test.ts` 的 TS⊆Rust
> 契约、`rcCapability.test.ts` 的禁区清单）都是 fitness function——本文做的事是把这个
> **已经验证有效的模式扩展到死代码维度**，不是引入新宗教。

## 1. 第一道防线：门禁（fitness functions）

### 1.1 JS/TS 死代码：knip 为标准工具

**为什么是 knip 而不是自己写脚本**：2026-11-21 探针实测（见附录 A），手写闭包脚本只能查
「文件不可达」，查不了「导出未用」——knip 一次报出 36 个未用导出 + 3 个孤儿 CSS + 1 个未用依赖，
全部是手写脚本的盲区。knip 是入口图分析的专业实现，有 200+ 框架插件（Vite/Vitest 都在内），
且「缺入口就报假阳性」的行为本身就是**逼着入口配置保持最新**的机制。

**入口配置（本项目的真实入口，探针逐个验证过）**——`desktop/knip.json`：

```json
{
  "$schema": "https://unpkg.com/knip@latest/schema.json",
  "entry": [
    "index.html",
    "rcask.html",
    "motion-preview.html",
    "src-mobile/index.html",
    "src/design-preview/main.tsx",
    "scripts/*.mjs"
  ],
  "project": ["src/**/*.{ts,tsx,css}", "src-mobile/**/*.{ts,tsx,css}", "scripts/**/*.mjs"],
  "ignore": [],
  "ignoreDependencies": []
}
```

四个入口的来源（漏任何一个，knip 会把整条链误报成死代码——**这正是探针里
`switch/tabs/Collapse/useCountUp/design-preview` 被误报的根因**）：

| 入口 | 消费方 | 漏了会误杀 |
|---|---|---|
| `index.html` → `src/main.tsx` | 主工作台窗口 | 几乎全部前端 |
| `rcask.html` → `src/rcask.tsx` | 入站申请浮层窗（`rc/ask_pop.rs` 指过来） | RcAskPop 链、WindowCrashFallback |
| `motion-preview.html` → `src/design-preview/motion.tsx` | 动效设计评审页 | design-preview 全家 + ui/switch、tabs、Collapse、useCountUp、pageTransition |
| `src-mobile/index.html` → `src-mobile/main.tsx` | 手机端独立构建（`vite.config.mobile.ts`） | 整个 src-mobile |
| `scripts/*.mjs` | package.json scripts / 手动工具 | 构建脚本全家 |

🔴 **规则：新增入口必须同步 knip.json**。入口包括但不限于：新 html 页、新 vite 构建配置、
新的 npm script 引用的脚本文件。CI 红一条「unused files」时，第一反应是「我是不是漏了入口」，
**不是把它加进 ignore**——knip 文档原话：teach knip, don't silence it。

**已知 knip 盲区（本项目实证，删前三查兜底）**：`vi.mock()` 引用的文件 knip 不视为在用
（`RcPairModeSelect.tsx` 实例）。这类文件删除前必须 grep `vi.mock`。

### 1.2 棘轮原则：基线只降不升

存量烂账不允许「一步灭零」吓退人，也不允许「算了不改」烂回去。采用 Theodo 的棘轮法：

1. 探针跑出的当前计数写进 `knip.json` 旁的基线文件（或门禁脚本里的常量），如
   `MAX_UNUSED_EXPORTS = 36`；
2. 每次清理往下调，**只许降不许升**——新增未用导出直接红；
3. 降到 0 后切换严格模式（`knip` 无参数即退出码非 0）。

> 本项目组件体量门禁已是完全同形的棘轮（基线只降不升），knip 计数是同一模式的第二个实例。
> **写死代码数和写死函数一样，都是数字，不是态度。**

### 1.3 Rust 侧：clippy 已覆盖大半，补 machete 管依赖

- `dead_code` / `unused_imports` / `unused_variables` 等 lint **编译器默认开启**，门禁已有
  `cargo clippy --all-targets -- -D warnings`——Rust **代码级**死代码已经被门禁挡住，
  这是 Rust 相对 TS 的结构性优势（TS 的 `noUnusedLocals` 只管文件内，管不了跨文件导出）。
- 缺口在**依赖级**：2026-11-21 刚抓到的 `thiserror`（根 Cargo.toml 声明、项目零使用，
  vendored noq-proto 自带声明）就是这一类。补 `cargo-machete`（文本级扫描、秒级、
  CI 友好；文档明确建议 CI 用 machete、偶尔手工跑需要 nightly 的 cargo-udeps）：

```toml
# desktop/src-tauri/Cargo.toml（误报抑制：经宏/构建脚本间接使用的 crate 列这里）
[package.metadata.cargo-machete]
ignored = []
```

新增 Rust 依赖时在 PR 描述里写一句用途；machete 报 unused 时，删依赖或进 ignored 并注释原因。

### 1.4 一条规则只有一道闸

cross-stack-standard ADR 0062 的决策，直接采纳：**同一规则不允许两个工具重复执法**——
重复的闸会漂移、会双报、会让「以为有人管」其实没人管。本项目的分工：

| 规则类型 | 执法工具 | 理由 |
|---|---|---|
| 跨文件图（未用文件/导出、依赖、环） | knip | 只有它做全图分析 |
| 单文件内（未用变量/import） | eslint + tsc | 编辑器实时反馈 |
| Rust 代码级死代码 | clippy（已有） | 编译器原生 |
| Rust 未用依赖 | cargo-machete（新增） | 唯一轻量选项 |
| 架构分层/域边界 | dependency-cruiser（见 §2） | 需解析后图谱 + 反向引用 |
| 接线契约（TS⊆Rust、五环挂载） | 对账测试（已有） | 语义级，静态工具表达不了 |

## 2. 第二道防线：结构边界（让死代码无处躲）

死代码的温床是**缠成一团的结构**：一个 300 行组件同时被 5 个页面引用，谁都不敢删。
边界清晰的代码，删除是局部动作。

### 2.1 分层单向依赖

本项目已天然分两层（沿用即可，不必新发明）：

```
壳子层   src/main.tsx / App.tsx / components/（非 rc）/ lib/（非 rc 前缀）/ contexts/ stores/
rc 域    src/components/rc/ / src/lib/rc* / src/hooks/useRc* / src/stores/rc*
```

规则（**方向只许向下，壳子层不 import rc 域**——rc 域是可以整体移除的交付单元，
壳子层不是）：

- rc 域文件统一 `rc` 前缀命名（**已是现状**，`rcPlatform.ts` 注释里有同样决策记录）；
- 壳子层禁止 import `rc` 域——remote 功能整体下线时壳子层零改动；
- 手机端 `src-mobile/` 是独立构建，与桌面端只允许经 `src/lib/` 的跨端契约层相遇
  （`rcTypes.ts` 等字节契约文件），不允许直接 import 桌面组件。

### 2.2 执法：dependency-cruiser 形式化已有手写规则

`rcCapability.test.ts` 的 `FORBIDDEN_ZONE`（禁区清单）是手写的 fitness function——
有效，但表达力有限（只能枚举文件，不能表达「层间方向」「环」）。用 dependency-cruiser
把同规则搬上解析后图谱：

```js
// desktop/.dependency-cruiser.cjs（首批规则，随违例增长）
module.exports = {
  forbidden: [
    {
      name: "shell-not-import-rc",
      comment: "壳子层禁止 import rc 域（rc 是可整体移除的交付单元）",
      severity: "error",
      from: { path: "^src/(components/(?!rc)|lib/(?!rc)|contexts|stores/(?!rc)|hooks/(?!useRc))" },
      to: { path: "^src/(components/rc|lib/rc|hooks/useRc|stores/rc)" },
    },
    {
      name: "no-orphan-modules",
      comment: "禁止成为只有自己引用的孤儿模块（死代码温床）",
      severity: "warn",
      from: {},
      to: { path: "^src/lib/[^/]+\\.ts$", numberOfDependents: "exactly0" },
    },
    {
      name: "no-circular",
      severity: "error",
      from: {},
      to: { circular: true },
    },
  ],
  options: { tsConfig: { fileName: "tsconfig.json" } },
};
```

存量违例先登记基线（**基线只缩不涨**，同 §1.2 棘轮），新违例直接红。
`eslint-plugin-boundaries` 给编辑器实时反馈，dependency-cruiser 管全图——一处执法不重复。

### 2.3 导出最小化：default 是私有的，export 是承诺

36 个未用导出（探针实录）的成因都一样：**顺手 export**。规则：

- 导出 = 对外承诺 = 维护负担。文件内用的一律不加 `export`；
- 删除顺序：先 `knip --fix` 摘 export 关键字 → 声明变未用 → 整行删掉。knip 文档原话：
  「摘掉 export 可能暴露更多未用代码， rinse and repeat」；
- 类型导出同样算（探针里 22 个未用类型）。

## 3. 第三道防线：流程与文化

### 3.1 童子军军规（Uncle Bob, Clean Code）

> 「离开时比发现时更干净。」Google 版的表述：**you touch it, you own it。**

三条边界（防 yak shaving，来自实践总结）：
1. **只在动过的地方附近清**——本次任务打开的文件/模块，不顺藤摸瓜全仓扫；
2. **15 分钟上限**——更久的清理开独立 commit/PR，不混进功能提交；
3. **不改行为**——纯结构/命名/删除，测试必须原样绿。

### 3.2 删除四查（2026-11-21 实证沉淀，🔴 每查都拦下过假阳性）

初版死代码审计报告 6 个假阳性，全靠这四查拦下。**删任何「看起来死了」的文件前，四查全过才动手**：

| # | 查什么 | 挡下过谁 |
|---|---|---|
| 1 | **入口闭包**（4 个真实入口逐个确认） | RcAskPop 链、WindowCrashFallback、design-preview 全家、useCountUp |
| 2 | **测试引用宽匹配**（import 边 + 字面量拼接路径 + `vi.mock` 别名） | RcPairModeSelect（vi.mock 不带扩展名，grep 文件名也抓不到，必须 grep `vi.mock(`） |
| 3 | **构建配置引用**（vitest setupFiles/alias、tsconfig、html 的 script/link 标签） | test-setup.ts×2、__mocks__×3、vite-env.d.ts（import.meta.env 类型） |
| 4 | **脚本/工具路径引用**（scripts/、CI、构建产物生成器） | design-preview/main.tsx（build-design-preview.mjs 按路径引） |

宁留不删。git 历史就是后悔药——**删错一个文件的代价远小于删错后三个月的静默故障**。
（探针实证：knip 无配置时 22 个「未用文件」里 15 个是假阳性，全部命中上表。）

### 3.3 PR 定义完成（Definition of Done）

`.github/PULL_REQUEST_TEMPLATE.md` 增补勾选项：

```markdown
- [ ] 新增文件有真实消费方（knip 绿；若是新入口已同步 knip.json）
- [ ] 删除的文件过「删除四查」（§3.2），无 vi.mock / readFileSync / 配置引用残留
- [ ] 新增 npm/Rust 依赖在描述里注明用途（防 thiserror 式死依赖）
- [ ] 本次改动触达的过期注释/CHANGELOG 已同步（删了源码就要删它的注释）
```

### 3.4 债档与例行化

- **债档 = 活文档**：`docs/项目体检报告-*.md` 即债档（位置/性质/工时/影响 四字段），
  发现即登记，清一条划一条，不凭记忆；
- **月度例行**（30 分钟）：全量 `knip` + `cargo machete` 跑一遍，与基线对账，
  增量进债档。Rust Project Primer 的建议：依赖检查不必每次 PR 跑，按周期即可；
- **容量配比**：Google/Atlassian 的 20% 法则（每冲刺 20% 容量还技术债）对两人团队
  翻译成人话：**每个迭代至少一个清理 PR**。宁可小，不可无。
