## 0. 结论先行

调研后发现 **P1 不是「让 iroh 支持 v6」——iroh 层大部分已就绪**。
真正的缺口在 DeskPanda 自己的两层(LAN 发现层纯 v4、路径可见性不分族)
和一处对 P0 的反向约束(自建中继必须双栈)。按性价比拆成三步,
第一步半天,第二步是主体,第三步是验收。

## 1. 现状盘点(实查证据)

### 已就绪(零改动)

| 项 | 证据 |
|---|---|
| 端点**默认双栈绑定** | iroh endpoint.rs:328「builder 总是预配 `0.0.0.0` + `[::]`(v6 允许失败)」;DeskPanda 未动 bind_addr ⇒ v6 socket 已在绑 |
| QAD 自动发现公网地址(含 v6) | `DirectAddrType::Qad`「QAD 发现的公网出口地址」;观测到什么族取决于去中继的路径(见缺口 G2) |
| pkarr 发布「全部传输地址」 | iroh address_lookup.rs:23「publish 收到完整传输地址集,可过滤」 |
| 诊断层**按协议族分治** | `net/diagnostics.rs:20`(v4/v6 分开判,iroh 的 `mapping_varies_by_dest()` 做 \|\| 聚合会把 v4 连坐——已收口);对称 NAT **按族放弃**不连坐另一族 |
| 会话路径从活连接实测 | `net/path_kind.rs`(用 `Connection::paths()`,非推断) |
| 连接地址天然多族 | `EndpointAddr.addrs: BTreeSet<TransportAddr>`(iroh-base endpoint_addr.rs:46),`with_addrs()` 可装任意族 |

### 缺口(按影响排序)

| # | 缺口 | 实查证据 | 影响 |
|---|---|---|---|
| **G1** | **LAN presence 层纯 IPv4** | `net/mcast.rs:17-83`(`Domain::IPV4`、`Ipv4Addr` 组播组、v4 网卡枚举);`presence/wire.rs:144`(报文只带 `port`,「IP 由接收方从源地址取」) | ①纯 v6 网段(访客 Wi-Fi 常禁 v4 组播)完全互相不可见;②双栈 LAN 只会学到/尝试 v4 直连,v6 局域网路径(常更稳,无广播风暴)被浪费 |
| **G2** | **QAD 的 v6 发现依赖中继双栈** | QAD 观察的是「中继看到的源地址」;客户端经 v4 连中继 ⇒ QAD 只报 v4。n0 三台(use1/euw1/aps1)的 v6 支持未验证 | 公网 v6 直连的**地址发布**环节断链:即使本机有公网 v6,对端也拿不到这个候选地址 |
| **G3** | **路径可见性不分族** | `path_kind.rs` 只有 lan/direct/relay;诊断卡有 `global_v6`(探测值)但会话里看不出**实际**走了 v6 | 验收无法判「v6 直连成立」;排障分不清 direct=v4 还是 v6 |
| G4 | 地址尝试顺序不可控 | iroh 内部对 `EndpointAddr.addrs` 候选的 race 顺序无公开 API 控制 | 理论上「优先」可能不成立——但 QUIC 路径迁移会选最先打通/最优路径,实践上「给全候选」即可,见 §3 决策 C |

## 2. 与 P0 的相互约束(🔴 回写)

1. **P0 自建中继的 VPS 必须双栈**(v4 + v6/64 以上):中继是 QAD 的观测点,中继没 v6,客户端的公网 v6 地址就永远不会被发现/发布。回写进交接文档 §5.1 的服务器要求与 P0 方案稿 §6。
2. 诊断卡现有 `udp_v6 / global_v6` 探测值可在部署后直接当验证器:relay 双栈 ⇒ global_v6 开始有值。

## 3. 设计决策

### 决策 A · G1 的修法(LAN presence 双栈化)

| 方案 | 说明 | 判断 |
|---|---|---|
| **A1(推荐)** | **v6 组播收发 + 保持「IP 取源地址」协议**:新增 v6 组播 socket(`ff02::xxxx` link-local scope,逐网卡 join),v4/v6 双发双收;`Wire` 报文格式**一个字节都不改**(v6 包的源地址照样进地址表) | 改动集中在 `mcast.rs`(新增 v6 族)与 `presence/socket.rs`(双 socket 收发);协议零改动 ⇒ **新旧版本互通、字节兼容**(与 wire.rs 既有的兼容纪律一致);v4 路径零风险 |
| A2 | Wire 增加自报地址列表字段(v4+v6 全量) | 改线上协议(可向后兼容),但「自报地址」不可信、且源地址本来就有——多此一举;否 |
| A3 | 只做 G3 不动 LAN 层 | 纯 v6 网段仍然互相不可见;不足以宣称「P1 交付」;否 |

A1 的两个实现要点(写进实现,评审时重点看):
- **fe80 link-local 与 scope_id**:v6 源地址可能是 `fe80::`(带网卡 zone)。`SocketAddrV6` 携带 `scope_id`,入表/连接都保留;序列化 `EndpointAddr` 时 iroh-base 已处理(TransportAddr 含完整 SocketAddrV6)。**优先采纳 ULA(fd00::/8)/全局 v6 候选,fe80 作末位兜底**(fe80 跨网卡即失效,scope_id 只在本机有意义)。
- **组播组地址**:v4 用现有组;v6 新开 `ff02::` 下与 v4 组同编号的组(link-local 域,不跨路由器,与 v4 组播的可达域对齐)。

### 决策 B · G3 的修法(路径族标注)

- `net/path_kind.rs`:`PathKind` 增加 `DirectIp` 信息或在 `direct` 上带族标记——**对前端的序列化值**新增 `direct-v6`(v4 保持 `direct` 不动,旧前端读不懂的枚举值只在新增侧出现)
- 设备行 `last_path` 与会话横幅显示「直连(IPv6)」;诊断卡已就绪不用动
- 🔴 排查点:`rc_devices.last_path` 是落库字符串,加新值前 grep 全部消费方(前端 switch/映射)确认无 default 分支炸掉

### 决策 C · 「优先」的口径(诚实降级)

不引入显式优先级控制(iroh 无公开 API 保证候选顺序):
1. **给全**:presence 学到的 v4/v6、QAD 的 v4/v6、pkarr 解析的全部进 `EndpointAddr.addrs`;
2. **让 QUIC 竞速**:连接层自然选最先打通的路径;v6 通常 RTT 更优(无 NAT 开销)会胜出;
3. **可观测**:G3 的族标注让「v6 是否真的在赢」看得见——数据说话,若实测发现 iroh race 偏 v4,再上游提 issue 或在 `addrs` 集合里做启发式排序(那时有证据)。

## 5. 验收判据

- [ ] P1-a:强制 v6 直连的会话,设备行/横幅显示「直连(IPv6)」;v4 直连与会话全部零变化(CI + 手测)
- [ ] P1-b:同一 LAN 禁用 v4 组播(路由器/AP 设置)后,两台设备仍互相可见、可直连;双栈下地址表同时出现对端 v4+v6
- [ ] P1-c:两台不同家庭宽带(或家宽↔5G 热点)且两端都有公网 v6 的机器,打洞成功走 `direct-v6`;诊断卡 `global_v6` 有值
- [ ] 全程:v4-only 环境(现状大多数)行为逐字节不变(回归靠 800 测试 + S5 清单抽查)

## 6. 风险

| 风险 | 口径 |
|---|---|
| v6 组播在部分网卡/AP 被 drop | 与 v4 组播同等命运;双发双收本来就是「多一条路」不是「换路」,最坏退回现状 |
| fe80 + scope_id 的跨机语义 | scope_id 只在本机有效:入表时保留、**使用时仅当与出接口一致才拼**;实现里对 fe80 做末位兜底 |
| iroh 候选 race 偏 v4 | 决策 C:先可观测,有证据再干预 |
| Windows 防火墙对 v6 UDP 的默认策略 | S5 清单已要求放行防火墙(公用/专用);v6 同样适用,验收覆盖 |
