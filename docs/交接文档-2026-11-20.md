## 4. 本次会话已完成的工作(2026-11-20)

### 4.1 项目全面评估(已完成)

结论:工程纪律罕见严格(守卫测试/棘轮门禁/事故档案注释/零 TODO),核心短板在平台单一、vendor fork 维护负担、迁移残留死代码、无媒体管线端到端测试。问题清单(按优先级):

**高**:
1. macOS 远程功能未交付(S6)
2. 协议无版本协商——两端版本不一致直接连不上且无提示
3. vendor/noq-proto 是 trait 级 fork,升级必然冲突;`rc/media_flow.rs:504` 还引用了 vendor 源码行号
4. `tauri.conf.json` 的 `csp: null` + `dangerousInsecureTransportProtocol: true`
5. `rc/underlay/fetch.rs` 运行时从个人仓库下载执行二进制(默认关,供应链风险)
6. 媒体管线无自动化端到端测试

**中**:死代码 ~1300 行(`components/layout/` 全部、`tabs/`、`RcOverlay.tsx`)、TanStack Query 零使用空挂、IPC 类型手工镜像、`Result<_, String>` 弱类型、`commands/rc.rs` 2025 行超红线、UpdateContext.tsx 568 行在门禁扫描范围外、macOS 仅 ad-hoc 签名无公证。

### 4.2 打洞技术调研(已完成,结论如下)

**诊断(为什么卡)**:
- iroh 打洞对对称 NAT 无解([iroh#4134](https://github.com/n0-computer/iroh/issues/4134)):只在对端是「无过滤的端口无关映射 NAT」时才能穿透对称侧;国内 CGNAT/双 NAT 场景高发。
- 打洞失败回落 n0 公共中继(use1 美东/euw1 欧洲/aps1 孟买),全跨境,延迟高抖动大。
- 实验性 EasyTier underlay 默认关(`rc/underlay.rs`,feature `easytier-underlay` + 配置项双开关)。
- 对照:UU 远程弱网实测直连率 ~92%,靠「加速器级打洞 + 国内 200+ BGP 中继节点」两头赢;Tailscale 直连 >90%,硬 NAT 用生日攻击,双侧硬 NAT 放弃打洞走自建 DERP。

**四层方案路线图(按见效速度)**:
1. **P0 自建国内/香港中继**(1-2 天,已选定下一步,细节见 §5.2)
2. **P1 IPv6 直连优先**(几天;国内家宽/5G 普遍有公网 v6,双 v6 直连率 100%)
3. **P2 对称 NAT 主动攻击**(2-4 周;生日攻击端口喷洒——单侧硬 NAT:硬侧开 256 socket、软侧 ~1024 探测包 → 98% 成功、2048 → 99.9%(约 20s);双侧硬 NAT 不实用走中继。**落点:underlay 框架内原生实现,成功后经 QNT ADD_ADDRESS 注入现有 QUIC 连接,不换流**)。参考:[Tailscale: How NAT traversal works](https://tailscale.com/blog/how-nat-traversal-works)、[iroh#2317](https://github.com/n0-computer/iroh/issues/2317)(端口预测,论文宣称 97%)
4. **P3 EasyTier 保留为兜底的兜底**(二进制换官方 Release 源 + 独立校验,解决供应链问题后再考虑转正)

## 5. 当前工作流:P0 自建 iroh-relay(下一步,未动手)

### 5.1 要求清单(已调研核实)

| 项 | 要求 |
|---|---|
| 服务器 | 香港**多线 BGP** VPS(免备案,延迟 30-50ms;大陆机器需 ICP 备案但延迟最优),1-2C/1-2G 起步,瓶颈在带宽 |
| 带宽 | 中继会话双向全码率转发:均衡档 8Mbps ≈ 7GB/小时/会话;按带宽计费建议 ≥30Mbps |
| 端口 | **80/TCP + 443/TCP**(ACME + relay 本体);可选 QAD 的 UDP 端口(默认 7824,`enable_quic_addr_discovery = true` 开启,类 STUN,提升打洞质量) |
| 域名 | 必须,提前 DNS 解析到 VPS;TLS 用内置 ACME 自动签发 |
| 版本 | iroh-relay **必须与客户端 iroh 1.1 同仓库同版本**(协议随版本演进) |
| 防滥用 | 默认对全网开放,必配 `access.shared_token`(客户端 `RelayMap::with_auth_token`) |

### 5.2 服务端配置模板(官方口径)

```toml
# /etc/iroh-relay/config.toml ;启动:iroh-relay -c config.toml
http_bind_addr = "[::]:80"

[tls]
https_bind_addr = "[::]:443"
hostname = "relay.你的域名"
cert_mode = "LetsEncrypt"
cert_dir = "/var/lib/iroh-relay/certs"
contact = "you@example.org"

access.shared_token = ["随机长token"]
```

健康检查:`curl --noproxy '*' --fail https://relay.你的域名/healthz`。安装:GitHub Releases 二进制 / Docker `n0computer/iroh-relay` / `cargo build --profile optimized-release --package iroh-relay --features server`。完整配置项以仓库 `iroh-relay/src/main.rs` 为准(官方文档自认不成文)。

### 5.3 客户端改动点(DeskPanda 侧)

- 文件:`desktop/src-tauri/src/net/endpoint.rs` 的 `get_or_bind()`(现用 `presets::N0`)。
- 改法:`RelayMode::Custom(RelayMap::from_iter([自建URL, n0兜底URL]).with_auth_token(token))`,自建排前。
- 🔴 **URL 和 token 用编译期常量**,不读环境变量——仓库自己的教训(CHANGELOG 2026-11-20:Gitee 镜像踩过「装在用户机器上的应用读不到 env」);运行时 env 仅作本地调试覆盖。
- 建议同时:relay 配置做成可灰度(设置页/编译期默认值 + env 覆盖),并让 `rc_net_diag` 面板显示「当前走的哪个中继」便于验收。
- 验收:两台 Windows 双机,制造打洞失败场景(如双 CGNAT/热点),确认会话回落到自建中继且流畅;对照 `docs/S5-双机验收清单.md` §6.5(中继路径判据)。

## 6. 仓库纪律速记(改动前必看,细节以 CLAUDE.md 为准)

1. **先出方案再动手**,涉及取舍给 2-3 方案对比;复杂任务进 Plan Mode。
2. **版本号唯一真源** = `desktop/src-tauri/Cargo.toml`;日常改动不动版本,只往 CHANGELOG 的 `[Unreleased]` 加条目;只有明确说「打 tag」才走 `npm run release`。
3. **UI 改动先出 HTML 设计稿**(放 `design/`,不入库)再改代码。
4. **等用户说「提交」再 commit**;提交前逐文件审 diff,绝不 `git add -A`。
5. 门禁 7 项(pre-push 自动跑):组件体量/fmt/eslint/tsc/vitest/clippy/cargo test;Rust 三条用 `--no-default-features`(测试二进制瘦身)。
6. 组件红线:`.tsx` ≤300 行且 useState+useEffect ≤8,棘轮制;`lib/` 新主题另开文件,不往 `utils.ts` 堆。
7. 文档放 `docs/`、命名用中文 + 日期后缀(本文档即按此规则);换行符 LF。
8. `security/path.rs` 路径白名单任何改动不得削弱。
